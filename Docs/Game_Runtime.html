Game state, timing, and events

Appeal docs · Language reference

This reusable Appeal script supplies one game's lifecycle and clocks. The host owns its loop, input, simulation, rendering, and game-specific reset behavior. No modules, plugins, database, window, or assets are required by the runtime itself. Load the script once per interpreter.

Run Libraries/Game/Runtime
Call Game_Start

// Inside your existing host loop, once each frame:
Call Game_Update
Call Game_Dispatch_Events
// Update your simulation using Game_Delta_Seconds, then render.

Keep updating and dispatching while paused or stopped so menus and real-time timers remain responsive. Do not call the gameplay simulation when paused/stopped. A zero delta is not a substitute for guarding actions that do not depend on time. The runtime does not automatically pause Audio, Mechanics, Physics, Graphics animation, or World; the host must gate/update those systems appropriately. Existing modules with their own clocks are not automatically driven by these deltas.

Basic script functions

CallBehavior
Call Game_StartReset both clocks, deltas, fixed-step backlog, pending events, and timers; preserve bindings and configuration. Set running, clear pause, select Playing, and queue Game_Started. Does not recreate game objects or reset score.

Basic events and timers

Clock_Milliseconds and Events are built into Appeal. No dynamic module is needed. Events are asynchronous within the host's single thread: Emit queues work; Dispatch runs handlers.

Define_Function Show_Message
    Print Var Event_Value
End_Function
Events Bind Message Show_Message
Call Game_Start
Events Emit Message "Hello now"
Events After Greeting 1000 Message "Hello after one gameplay second"
Events After_Real Reminder 2000 Message "This timer also advances while paused"
// Continue calling Game_Update and Game_Dispatch_Events in your loop.
CommandArguments and behavior
Clock_MillisecondsReturn fractional milliseconds since this interpreter was constructed, using std::chrono::steady_clock. Monotonic, not a calendar timestamp or an audio clock.
Events Bind Event FunctionBoth names are nonempty strings. Function must already be defined. Multiple handlers run in binding order; binding the same pair twice has no effect.
Events Unbind Event FunctionRemove that binding. Missing bindings are harmless.
Events Emit Event ValueQueue a named event with one string payload; use "" for no payload. Numbers may be carried as strings. Event name must not be empty.
Events After Timer Delay Event ValueSchedule a one-shot event relative to the current gameplay clock. Delay is finite, nonnegative milliseconds. Reusing the timer name replaces it. Zero delay becomes due at the next clock update.
Events After_Real Timer Delay Event ValueThe same operation using unscaled real elapsed time, including paused/stopped frames. Timer names are shared across both clock domains.
Events Cancel TimerCancel a timer that has not expired. Missing timers are harmless. Does not remove an already queued expiry event.
Events PendingReturn the number of queued events, excluding the batch currently being dispatched.
Events Timer_CountReturn the number of scheduled timers.
Events ClearDiscard queued events and the remainder of an active dispatch batch. Preserve timers, clocks, and bindings.

Timers expire during Game_Update/Game_Advance. If several expire in one update, they queue in timer-name order, after events already queued. They run at dispatch time, not at an exact wall-clock instant. For repetition, schedule the next timer in its handler. This deliberately skips missed intervals rather than producing a catch-up burst.

Advanced functions

Call/commandBehavior
Set_Var Game_Elapsed Milliseconds
Call Game_Advance		Inject elapsed time instead of reading the clock. Useful for deterministic tests or an external clock. Negative elapsed time becomes zero; invalid/nonfinite arithmetic fails. Do not alternate with Game_Update without rebasing Game_Last_Clock.
Call Game_Next_StepExpression function returning 1 if a fixed simulation step is available, otherwise 0. Consumes Game_Fixed_Delta from the accumulator and sets Game_Step_Seconds. Does not update module clocks or run simulation for you.
Call Game_Reset_ClockReset clocks/backlog, timers, and pending events without changing state/running/pause/configuration/bindings. Rebase the wall-clock measurement.
Events Update GameMilliseconds RealMillisecondsAdvance the native timer clocks and enqueue expiries. Both arguments must be finite, nonnegative, and nondecreasing. Normally managed by Game_Update/Game_Advance.
Events Dispatch LimitDispatch a snapshot of at most Limit events; integer 1..65536. Events emitted in handlers wait for a later dispatch. Nested dispatch is rejected. No return value.
Events ResetClear timers and events, cancel any active batch remainder, and reset native clocks to zero. Preserve bindings. Normally managed by Game_Start/Game_Reset_Clock.

Events are FIFO. The handler list is copied for each delivered event; binding changes affect subsequent events. During each handler, Event_Name and Event_Value contain that event's strings. Their previous values (or absence) are restored after dispatch, including on error. Reset/Clear inside a handler cancels the remaining handlers and events in the active batch; newly emitted events survive for the next dispatch. A handler error stops execution; the selected batch is not retried. Queue and timer capacities are each 65536; exceeding either reports an error.

Optional fixed-step simulation

// After defining Simulate_One_Step, use this instead of variable-delta simulation:
Call Game_Update
Call Game_Dispatch_Events
Loop While (Call Game_Next_Step) == 1
{
    Call Simulate_One_Step
    // That function uses Game_Step_Seconds, not Game_Delta_Seconds.
}
// Render once, outside the simulation loop.

The default step is approximately 1/60 second. At most eight steps are consumed per frame; when a further step is requested after that limit, remaining backlog is discarded to prevent a catch-up spiral. Game_Max_Delta clamps real elapsed time before applying the time scale. Consequently gameplay time can intentionally lag wall time after a stall. Gameplay timers follow Game_Time, not the number of fixed steps actually simulated. This is not a lockstep networking or deterministic-physics guarantee. Consume the fixed steps each frame if using this path; do not run both variable and fixed simulation for the same objects.

Script variables (not module globals)

Names beginning Game_ are owned by this library. Read status/output variables; change only configuration or documented inputs. All times use double-precision arithmetic and milliseconds unless their names end in Seconds.

Lifecycle events: Game_State_Changed carries the new state; Game_Paused and Game_Resumed carry the current state; Game_Started, Game_Restarted and Game_Stopped carry an empty string. They are queued, not immediate callbacks. State changes happen immediately; event payloads describe each change even if another change occurs before dispatch.

Scope, cost, and validation

This first Step 1 implementation supplies reusable state/timing policy in Appeal with a small native clock, event queue, and named timer service. Native timer collection scans active timers once per update; callbacks execute Appeal scripts. High timer/listener counts or heavy handlers must be profiled in their actual game before adding more C++ acceleration. This layer does not yet prove integration of every module with one authoritative simulation clock.

Language simplicity finding: Return inside an If exits its anonymous block, not the enclosing function. Game_Next_Step therefore uses nested guards and one final Return_Value. Game authors do not need to repeat this implementation; an enclosing-function return is a possible future language improvement.

Run python Tests/Game_Runtime_Tests.py for lifecycle, pause/scaling, timer, event ordering/reentrancy, fixed-step, and monotonic-clock checks plus a small cost sample. Run Appeal.exe Examples/Game/State_Timing_Events for the headless example.
