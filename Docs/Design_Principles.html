Appeal Design Principles

Appeal is a general-purpose programming language and runtime. Bananas is the first major Appeal-based app, focused on game development. The same language and module API should later support other apps, including a browser that uses Appeal scripts instead of HTML and JavaScript.

Universal Scripts, Platform-Specific Plugins

Appeal scripts and modules should stay platform independent. Plugins are compiled for each platform and provide optimized native behavior behind the same Appeal command API. A game should be able to use the same script on a desktop, handheld, phone, or server while each system loads plugins and assets appropriate for its hardware.

Small Module Set, Broad Modules

Appeal should avoid a large number of narrow modules. Each module should cover a useful area of responsibility. For example, Graphics is a 3D system that also handles 2D rendering, text, and GUI controls, so Bananas and future apps can share the same rendering API.

Scripts First

Appeal app developers should build with Appeal scripts and assets. They should not need to edit C or C++ source code. Native source changes belong to Appeal runtime development, module development, or plugin development.

Resource-Conscious by Default

The design assumes limited resources first. Apps should work out of the box on modest systems and scale upward on stronger systems. Stronger platforms can use heavier plugins and richer assets; lower-resource systems can use lighter plugins and smaller assets while running the same game logic.

Repository-Based Distribution

Modules, plugins, and assets should come from dedicated repositories. Different devices or operating systems can select different repositories. Systems with handheld and docked modes can switch between configurations, including different Config.Appeal choices and asset sets.

Security in Plugins

Remote scripts should not be able to replace native plugins. Plugin installation and updates should come from trusted repositories and user-approved package operations. Browser-style Appeal apps should keep security in distro-managed plugins, so unknown script authors provide content while the user's trusted plugin set enforces permissions and safety.

Permission-Oriented Apps

Apps should eventually use permissions similar to mobile operating systems. Users should be able to grant and revoke access to capabilities such as network, storage, input devices, and plugin installation.

Validated Strings at the Boundary

Appeal script values are strings at the language boundary. Plugins cast those strings to the native types they need, validate them, and either clamp or reject values based on the function. Clamping is useful for harmless ranges such as volume. Rejection is better when an invalid value indicates bad data or unsafe behavior.

Network Direction

The Network module should be able to read commands from a server and run them like a script from a file. It should also download assets and update modules or plugins through trusted package flows. Early networking can be plain for debugging, then move toward encrypted, key-based authentication once the command path is proven.
