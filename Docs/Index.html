Appeal Documentation

Appeal is a general-purpose command-stream language with a cross-platform runtime, platform-independent modules, and platform-specific plugins.

Project Shape

The current project keeps the Appeal runtime, module source, plugin source, runtime resources, and documentation together while the API is still evolving.

  • Source/ contains the Appeal app and core runtime.
  • Modules/ contains platform-independent module source code.
  • Plugins/ contains platform-specific plugin source code.
  • Resources/Appeal/ contains Appeal scripts.
  • Resources/Appeal/Setup/ contains reusable setup scripts such as Config.Appeal and Graphics_Setup.Appeal.
  • Resources/Appeal/GUI/ contains reusable GUI scripts such as Graphics_GUI.Appeal.
  • Resources/Appeal/Test/ contains module, plugin, language, and demo test scripts.
  • Resources/Modules/ contains built module and plugin binaries used at runtime.
  • Resources/<Module>/ contains module resources, such as Resources/Audio/Music, Resources/Audio/SFX, and Resources/Graphics/Textures.

Current Conventions

Appeal app developers should build with Appeal scripts and assets. They should not need to edit C++ source code. Developers of Appeal itself can add modules or update plugins when the language and runtime need new native capabilities.

  • Main.Appeal is the default startup script. The app can also start from a named script argument for testing or launching directly into a game or tool.
  • Setup/Config.Appeal loads the default modules and plugins. Other setup scripts can configure specific systems.
  • Default module configuration scripts should use Default_<Module>_Config.Appeal when they are added.
  • Each module should have a Test_<Module>.Appeal script and a Test_<Module> plugin.
  • SDL plugins are the cross-platform default until more specialized plugins are available.
  • Backend plugin names should use Appeal_<BackendLibrary>_<Module>, such as Appeal_SDL2_Audio.
  • Debug is a standard command. It accepts On, True, or 1 to enable output and Off, False, or 0 to disable output.

Packaging Direction

Plugins should eventually list their third-party dependencies in a plugin manifest, so the package system can install build and runtime dependencies for each supported platform. Remote scripts should not be able to install or replace native plugins; plugin installation belongs to trusted repositories and user-approved package operations.

The planned repository model lets different systems use different plugin and asset repositories. A low-resource device can use lighter plugins and assets while still running the same Appeal script API as a higher-end system.
